# Operator Context

- Stable value: maintain momentum across creative and software projects with low cognitive overhead.
- Execution preference: deterministic local scripts first, local automation second, Codex only for code changes or reviewable plans.
- Stewardship preference: convert input into progress on goals, not isolated tasks.
- Approval boundaries: do not publish, deploy, merge, delete, spend money, use credentials, access production data, or send messages without explicit approval.
- Reporting preference: identify current milestone, next action, work classification, and required artifact.
- Demo-first handoff preference: for software work, put a stable, runnable proof surface in the operator's hands before asking them to reconstruct progress from a Log, plan, diff, or validation transcript.
- Operator responsibility: personally exercise the current candidate and give product-direction feedback; before accepting work, approving a merge or release, or delivering to a client, read and understand the relevant Log and QA evidence.
- Stable-showing preference: preserve one known-good stakeholder demo while a separate candidate changes. Never present an unverified candidate as the stable demo.
- Delivery preference: move observable work through an explicit candidate demo, independent Arcadia QA, release approval, post-release verification, and client-delivery record.
