# Lead session trials

This is a starting lens for future native-app Lead trials, based on one supervised Luna delivery. It accompanies the [accepted, inactive draft Plan](../plans/reduce-lead-friction-through-ten-bounded-session-trials.md), with a ten-trial ceiling. Acceptance does not activate it, authorize launches, create a role, reserve capacity, or change any gate. The active production Plan and its Action remain authoritative. Read [native-app-sessions](../agent-guidance/native-app-sessions.md), [session roles and briefs](../agent-guidance/session-roles-and-briefs.md), [Hacker recovery](../agent-guidance/hacker-recovery.md), and the current handoff before each trial.

## Before a trial

1. Read this guide at its current revision and the prior [Luna trial recovery record](../reports/frictions/20261015-luna-lead-trial-recovery.md); check its linked evidence and any newer handoff. Read the active Plan's exact Action to rule out overlap, the notes-to-self matches, and the indexed procedures for the operation.
2. Name one comparable friction hypothesis, one bounded deliverable, and observable acceptance. Start a fresh Lead for each Action. A native Lead simulates unattended behavior; opening a task in an app does not enroll it in Arcadia, grant authority, or reserve model capacity.
3. State each participant's actual model and effort from launch evidence, and state the trial's explicit usage/spend allowance and stop point before launch. Unknown usage is unknown, never zero. If the allowance or authority is absent, do not launch; preserve a proposal for the operator through the governed path.
4. Follow the existing one-writer loop: Lead supervises; one implementer owns writes; reviewers are independent sessions. Use existing commands and records. Do not add wrappers, tools, or parallel status tables.

## Progress gates

Record evidence at each gate. Advance only when that gate is evidenced and the next step remains within scope and authority.

1. **Useful bounded hand-back.** The assigned output exists and meets its acceptance. A research-only or no-diff hand-back does not count as delivery: diagnose briefly, preserve the assignment, and stop commissioning that unchanged work. Record what was and was not delivered.
2. **Sole-writer delivery.** Where code is needed, one implementer owns edits and returns a candidate/PR. Follow the current PR procedure for focused checks, candidate preservation, issue linkage, and the hand-off.
3. **Independent exact-head review and integration.** Require a fresh independent review of the current PR head with no unresolved blocking findings, all currently required checks green on that head, and a clean merge state. A new push resets proof as the PR procedure specifies. Review findings and CI are evidence; neither grants authority.

The cited PR had seven required checks; that count is historical, not normative. Read the current required-check configuration each time. Stop on authority boundaries, a safety regression, missing explicit budget, a hold, unclear ownership, or two unchanged workflow refusals without evidence gain; invoke Hacker recovery before another retry. A blocker is recorded and handed off, not routed around.

## When friction appears

- **Sandboxed `gh` cannot connect.** Check the active sandbox/granted profile and follow the normal host `require_escalated` route when authorized by the host and current procedure. Treat this first as a boundary question, not an outage; do not repeat the unchanged sandboxed call. See [working-copy safety](../working-copy-safety.md) and [PR procedure](../agent-guidance/pull-requests.md).
- **Delegate returns no diff.** Keep the same writer and assignment; ask one bounded clarification about the missing acceptance or evidence, then stop if it still cannot produce the deliverable. Do not replace the writer or reset its candidate to hide the hand-back. Preserve the hand-off under [native-app sessions](../agent-guidance/native-app-sessions.md).
- **A CI job failed but the overall run is still active.** Use available host check-progress events first. If unavailable, use a bounded wait and inspect the failed job's log; when current permissions allow GitHub API access, the existing route is `gh api --allow-escape-sequences repos/<owner>/<repo>/actions/jobs/<id>/logs`, captured to a temporary file with only bounded excerpts read. Do not dump full logs or keep polling without new evidence. Follow [PR procedure](../agent-guidance/pull-requests.md).
- **A commit identity looks wrong.** Resolve identity using [git identity guidance](../agent-guidance/git-identity.md), then set the resolved `GIT_AUTHOR_*` and `GIT_COMMITTER_*` environment for the commit. Do not use `git -c user.*` overrides.
- **A broker install/update is proposed.** Follow the current [rehearsal/freeze procedure](../agent-guidance/rehearsal-freeze-window.md) and exact reviewed clean-snapshot route only when that command and procedure currently allow it. Revalidate source revision, cleanliness, permission and production state; never patch raw source or infer blanket install authority from the prior trial.

- **A proposal is registered but acceptance fails.** Registration is not acceptance-readiness proof. Use the canonical two-phase `agent-ask settle` preview with the responsibility required by its validator. If a criterion fails validation, preserve it and register a minimally corrected revision under a new request id; validate every Action’s criteria before retrying. Apply only the exact accepted preview under current operator authority. Follow [Agent Ask settlement](../agent-guidance/agent-asks.md); never weaken the validator or infer activation from acceptance.

## Learning cycle

The proposed ten is a cap, not a quota or success claim. The original request `plan-lead-session-trial-learning-20261015` was superseded after the acceptance validator required explicit saved-brief proof. Revision `plan-lead-session-trial-learning-20261015-r2` was accepted on the operator’s direct instruction; [acceptance evidence](../reports/lead-session-trials/20261015-proposal-acceptance.json) records the applied receipt. The inactive draft Plan starts with five Actions: baseline, pilot 1, pilot 2, an independent checkpoint, and consolidation. Trials 03–10 would be added only through evidence-led governed amendments after that checkpoint; they are not pre-launched. Compare matched tasks and the same observable gates. Vary difficulty only after comparable repetitions; do not claim every run improves. Distinguish operator interventions (judgment or approval), supervisor actions (diagnosis and coordination), and host/tool prompts or permission steps. Count or cost them only when evidence measures them. Update the existing session ledger and friction record for each run; do not create a second trial-status ledger. Correct verified remedies and keep hypotheses visibly unresolved. Before the next trial, read the updated guide and prior hand-off, then choose one comparable friction to test.

Stop the cycle early if an authority or safety regression appears, the evidence cannot support a fair comparison, or the bounded allowance is exhausted. Use a governed Plan amendment to route reachable work to consolidation; never mark unattempted trials complete. The full series is large and staged, while the Plan writer currently hardcodes medium token-impact and generic budget metadata. Resolve suitable metadata and a finite aggregate allowance before activation; do not invent unsupported Ask fields. Further trials require governed authorization and explicit budget; this guide schedules nothing.
