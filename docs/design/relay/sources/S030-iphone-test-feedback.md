# S030: Operator's feedback after testing /workspace on an iPhone 15 Pro, 2026-11-04

The quotation below is verbatim.

> My feedback after testing /workspace on my iPhone 15 Pro.
>
> * The browser back/forward buttons must work. After tapping the Blocked pill, my view changes to a "YOUR MOVE" list with no way to get back to the previous view which held my context.
> * The dust storm background has way too much visual noise and motion, plus it's a bit jerky. I expect many users to consider it a gimmick, so we must always focus on function first and design extremely tasteful visual experiences that directly communicate the feeling associated with state. Transitioning between states can render more eye-catching visuals, but then must always stabilize to calm, meaningful, useful beautifully alive, dynamic presence. We're very close. Just think about rhythm and dynamics. Any effect that is too constant becomes invisible or annoying.
> * Tapping an `answer` tagged item in the "YOUR MOVE" list should be immediately responsive. Currently there is no indication that a tap event occurred until several seconds later when the browser navigates to the /todo page and spends over 10 seconds loading a Decision Answer card with pages of dense text. The Decision answering UX is absolutely crucial to perfect eventually, but for now I suggest that we focus on making Decisions seem lightweight.
> * Activity indication must always communicate when the system is working, ideally with information specific to what's happening. Tapping a link from the Blocked menu takes several seconds before the UI changes at all. It's unclear if the tap was received.
> * We should revisit many UX details around operator attention requests (To-dos, PRs, Decisions, etc.) and for now keep focusing on making the essential context navigation pieces much more lightweight, responsive and accessible. Currently everything is slow, dense, unresponsive, and confusing. A powerful Relay UI should eliminate the need for navigation in many cases since action can be taken on clearly presented issues using intuitive language and controls adapted perfectly to the operator's current context and need. Therefore, let's think about ways to dramatically simplify the UI's context layer with more abstract, symbolic, visual forms of communicating higher level concepts and summaries, rather than long, wordy lists of data that's largely irrelevant to the user's immediate activity. It's crucial to understand what the operator usage scenarios are! Why would an Arcadia operator be using the Workspace at all?
>    * Scenario 1: To provide some kind of input, usually clicking a button with reasons and consequences clearly stated in accessible language.
>    * Scenario 2: To create or modify a Project, Design, or Plan.
>    * Scenario 3: To observe and control production activity
>    * Are there any other important scenarios that Arcadia must support before launching?
