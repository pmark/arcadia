# Investigation: Relay first slice (Ask lookup routes, compact read tools, "Did you mean" menu, scorecard)

- **Investigator:** independent, read-only, depth one. Claude Code, model `claude-fable-5-1` (Fable 5.1). Runtime: Claude Code agent (sandboxed shell), 2026-11-03.
- **Evidence revision:** `refs/remotes/origin/main` at `76d812ad97fe5408dcb3356dc8b64eef4e52f678` after `git fetch origin main`. Every `path:line` below is on that revision unless marked. Nothing was run except `git`, `grep`, `awk`, `python3 -I` over probe JSON, and web search. No `arcadia` command, no model, no checkout.
- **Vocabulary used below:** "lookup route" = a read-only intake action; "menu" = the plan's "Did you mean…" card; "memo" = an operator correction replayed on exact text (`src/ask/corrections.ts`).

## The five things to change, ranked by value

1. **Build the compact renderers before any new routes.** The two lookup routes Ask already has (`show_status`, `show_review`) run the full commands and then show the operator *nothing*: the dashboard composer displays only `result.summary` ("Status shown.") and the Discord receipt never reads `data.status`. So the first observable value is a renderer for an existing route, not a regex for a new one. (Findings 1, 2.)
2. **Don't add a second router or new heard types. Add intake action kinds and reuse the `status` type.** `resolveIntake` already has the kinds, the confidence labels, the memo gate (`memoStandsDown`), the golden replay and the `Heard:` receipt. The plan's prototype (`routing-3-rules.py`) is a separate 16-tool router with its own hostile filter and its own conventions; porting it as-is would duplicate `src/intake` and break the golden set (Findings 3, 4, 7).
3. **Cut the menu's learning loop from the first slice; keep the menu.** The tap-to-memo loop needs a new correction type space (today memos route only to `work|idea|status`), a new menu identity to prevent stale/double taps, and a source that distinguishes a tap from a typed correction. The "three similar corrections → suggest a rule" part already exists (`MEMO_PATTERN_THRESHOLD`, `tokenPattern`); nothing new is needed there. A menu that only *shows* three options and records "which was tapped" in the existing `ask_requests` row delivers the measurement without the poisoning surface (Findings 5, 6, 8).
4. **Fix Project-name resolution before relying on "real Project names".** `scoreReference` scores 0.96 for any message that *contains* a Project name or alias of four or more letters, and the capture fallback resolves the Project from the whole raw text. A Project named `Scout` (the `arcadia-studio-scout` skill names one) claims every message with "scout" in it. Rules keyed on names will inherit this (Finding 9).
5. **Specify the scorecard as a held-out test with an error budget, keyed by surface, and make it the acceptance criterion.** The probe already has the right method (frozen rules, unseen set), but the plan's "50%, hopefully 80%" has no precision floor, no safety-zero clause, and no owner for the held-out set. Adopt: precision on claimed messages ≥ the next rung (today 94% for the 27B on the same set), zero production-lever or Decision mis-routes, and coverage reported, not targeted (Findings 12, 13).

## Numbered findings

### 1. The existing lookup routes return nothing visible on either surface — `must`, Improvement / Missed opportunity

- **Verified.** `src/commands/ask.ts:762-805` runs `runStatusCommand` for `show_status` and returns `result.summary: "Status shown."` with `status: status.data`. `apps/dashboard/app/api/ask/route.ts:46-49` responds with `message: response.data.result.summary` and `result: response.data`; `apps/dashboard/components/workspace/workspace-ask.tsx:125,193` renders `body.message` under the "Arcadia" heading and the trail cards, never `result.status`. `apps/discord-bot/src/formatters/requestFormatter.ts:52-112` builds the receipt from `heard`, `stewardship`, `intake`, `result.summary`, `workItem`, `reviewItemId`, `backBurnerItemId`; `data.status`, `data.review`, `data.projects`, `data.projectSummary` are never read.
- **Consequence.** "show status" through Discord today posts `Heard: status (high, rule) -> status shown (nothing created)` and a receipt saying "Result: Status shown." That is the operator's current experience of a lookup route, and it is what every new route in item 1 would reproduce until item 2 ships.
- **Change.** Make item 2 the first Action: a `compact` text for each read result (`status`, `review`, `project`, `projects`, and later `todo`, `prs`, `production`), produced in `src/` once and used by `heard.created`/`result.summary` so both the dashboard composer and the Discord receipt show it with no surface changes. The Discord `/arcadia status` slash command already has a six-line renderer (`apps/discord-bot/src/formatters/statusFormatter.ts:3-12`) that proves the shape and should be moved into the CLI rather than duplicated.

### 2. The compact read tools mostly exist as read-only commands; the gap is a compact *output*, not a new tool — `should`, Missed opportunity

- **Verified.** `src/commands/todo.ts:923,1043` (what needs me; `withReadOnlyDatabase`), `src/commands/now.ts:12-17` (one-screen "how far am I"), `src/commands/askTrail.ts:36-46` (what happened to an earlier request; `ask show` is the canonical name), `src/commands/capacity.ts:50-55` (allowance), `src/commands/workPullRequests.ts` (59 lines), `src/commands/wayLookup.ts:31` (Way passages, read-only, no database), `src/commands/production.ts` (status among other things), `src/commands/next.ts:53-65` (next Action; **writes** a journal row, see `withDatabase` at 63-65 and `docs/notes-to-self.md:224-226`).
- **Inferred.** The "23 to 717 KB in 2 to 4.5 s" figure (`docs/design/relay/record.yaml:2550,2659`) is about `--json` payloads. The plan does not say which commands were measured; `arcadia todo --json` and `ask show --json` are likely at the small end.
- **Change.** Specify each lookup route as `<existing command> + <compact renderer>`; never shell out to a command that writes (`next`, `ping`, `agent-ask preview`) from a lookup route. List the measured sizes per command in the Action so the "compact" criterion is testable (for example: compact text ≤ 1,200 characters, rendered in ≤ 300 ms from an open database).

### 3. The plan's prototype is a second router with different conventions from `src/intake`, and porting it would break the golden set — `must`, Risk (regression)

- **Verified.** `docs/design/relay/probes/routing-3-rules.py` has 16 tool names (`todo`, `next`, `prod_status`, `capacity`, `project`, `plan`, `action`, `trail`, `way`, `prs`, `prepare_off`, `prepare_start`, `answer_decision`, `capture`, `reason`, `chat`). Ask has five heard types (`src/ask/heard.ts:5`, `GOLDEN_TYPES` in `src/ask/goldenCases.ts:11`) and nine intake action kinds (`src/intake/index.ts:58-103`). Several prototype rules collide with pinned golden behaviour:
  - `reason`: `why is .* (slow|failing|broken)` would start claiming diagnostic questions, while `tests/fixtures/ask-golden.jsonl` `clarify-question` pins "Why does the archive feel slow?" as `unclear / Clarify First`.
  - `capture`: `^(build|make|create|add|set up|spin up)` overlaps `isImperativeRequest` and `parseInstantiateProject` (`src/intake/index.ts:460-470, 1494-1498`), which already decide `work` with `Requires Review` (`review-required-feature`).
  - `chat`: `^(thanks|ok|hi)` duplicates `isTrivialAcknowledgement` (`src/ask/suppression.ts:23-37`), which already suppresses acknowledgements and records `suppressed` on the Ask.
  - `todo`: `\b(need|needs|waiting|sign off|approve)\b.*\b(me|i)\b` would claim "approve the merge, I think" and other replies.
- **Change.** Treat the prototype as evidence only. Implement lookup routes as new `IntakeAction` kinds (`show_todo`, `show_next`, `show_production`, `show_pull_requests`, `show_plan`, `show_action`, `show_trail`, `show_way`) inside `resolveIntakeWithoutClassification`, placed *after* the existing high-confidence routes and *before* the `capture_thought` fallback (`src/intake/index.ts:546-566`), and route them all to the existing heard type `status` ("status shown, nothing created") so corrections, memos, the report's `ACTED_OUTPUT_KINDS` (`src/ask/report.ts:28-39`) and the coverage test keep working. Add one golden case per route plus one near-miss per route to `tests/fixtures/ask-golden.jsonl`; the `ask-golden.test.ts` second suite runs each through the real `arcadia ask`, so every new route gets an end-to-end check for free.

### 4. Only an exact-phrase matcher exists today; the probe's "rules handle 50%" is measured on a different population from the golden set — `should`, Risk (evidence)

- **Verified.** `isStatusRequest`, `isReviewRequest`, `isListProjectsRequest` are exact-string equality on a normalized text (`src/intake/index.ts:1304-1328`); `parseShowProject` is one anchored regex (1330-1339). The probe replayed 60 messages through this and got 58 low-confidence (`docs/design/relay/probes/routing-3.md`, "Rules"). The 46%/81% figures are for the Python prototype on 80 messages written by one agent, with 17 of 80 `capture` and 10 `chat` (counted from `routing-3-heldout-prompts.json`), so about a third of the "unseen" set is the two easiest classes.
- **Inferred.** Real operator messages will be shorter and more Project-specific than the probe's; "next for Harborlight?" style fragments were the probe's hardest cases, and they are the ones real Project names should fix.
- **Change.** Keep the coverage claim out of acceptance. Report coverage per class on the held-out set, and require precision per class, not overall.

### 5. The tap-to-memo loop extends a memo system that deliberately cannot do what the plan asks — `must`, Risk (memo poisoning / design)

- **Verified.** `MEMO_ROUTE_TYPES = ["work", "idea", "status"]` (`src/ask/corrections.ts:24`); `answer` is excluded by design (comment at 21-23). Memos are keyed on the exact normalized text (`normalizeAskText`, 51-54) and the newest operator correction wins (126-157). A memo carries a type and optional Project, not a *route* or a *tool argument*. `memoStandsDown` (167-173) protects only `Requires Review`/`Blocked`/unsafe intakes.
- **Consequence.** (a) A tapped "What's next for Scout" cannot be remembered as `show_next(project=Scout)`; it can only be remembered as `status`, which replays as the portfolio status. (b) A memo on "show prs" whose text later changes meaning (a Project renamed, a route removed) replays silently; there is no invalidation by registry version or route existence, only by Project id (`src/ask/goldenReplay.ts:64`). (c) The plan says "neither is remembered" for levers and Decisions, which the existing code already enforces for `answer`; `prepare` tools have no type at all, so nothing stops a `status` memo being recorded on "turn production off" if the menu offered it — the only guard is `memoStandsDown`, which requires the intake to have matched a concrete unsafe intent.
- **Change.** First slice: record the tap on the Ask row (`ask_requests.corrected_type` already exists, `corrections.ts:89`) with a new source value (`"menu"`) that is **not** in `OPERATOR_CORRECTION_SOURCES`, so it is counted by the report and the scorecard but never replayed. Defer replay until memos carry a route kind and Project id and are invalidated when the route or Project disappears. Keep the existing `MEMO_PATTERN_THRESHOLD = 3` hint path (`src/ask/memoPattern.ts:11-14`, `report.ts` `patternHints`) as the only "suggest a rule" mechanism; it already requires a reviewed PR.

### 6. Stale menus and double taps have no identity to bind to — `must`, Risk

- **Verified.** The dashboard Ask flow binds a request to `exchange.id` (`workspace-ask.tsx:172`) and refuses to resend while `phase === "uncertain"` (170). Discord replies are bound to a parent message id through `askReceiptMessageStatePath` (`messageCreate.ts:68,146-154`), and a Decision answer is bound to a review id. There is no equivalent for "option 2 of the menu attached to Ask X". Discord already uses number-plus-letter replies for Decisions (`messageCreate.ts:29`, `requiresReviewFormatter.ts:126-143`), so a bare "2" reply has no existing parser and would be a new Ask.
- **Change.** Give each menu an id and a fingerprint of its options (the dashboard's Decision cards already post "only the card id and the option's pinned fingerprint", `apps/dashboard/components/decision-cards.tsx:78-80`); a tap or number reply must name the menu id, and a second tap on the same menu id is idempotent. In Discord, accept a number only as a reply to the menu message (same mechanism as `askIdFromReceiptReply`), never bare. Expire menus after one newer Ask from the same operator.

### 7. Hostile text: the prototype's filter lists tool names and authority words; Ask's real protection is that lookup routes cannot write — `should`, Risk

- **Verified.** `routing-3-rules.py` `HOSTILE` matches `prepare_start|prepare_off|answer_decision`, `[admin`, `pre-authorized`; the probe itself says this "won't hold up against varied attacks" (`routing-3.md`, Limits). Discord fails open when `DISCORD_ALLOWED_USER_IDS` is empty (`messageCreate.ts:121-133`, `config.ts:68-72`), so any guild member in the channel can send an Ask; only `answer` corrections require a verified sender (74-81). `arcadia ask` can create a Project at high confidence (`ask.ts:863`) and update attributes (921-950, per R1-F6), which the decision interface already flags (`docs/design/relay/decision-interface.md`, "`arcadia ask` is not capture").
- **Inferred.** With no model in this slice, "hostile" text can only (a) trigger an existing write route, (b) get a bad memo recorded, or (c) make a lever confirm card appear. (a) exists today and is unchanged by the plan; (b) is finding 5; (c) is harmless only if the card itself needs a verified sender.
- **Change.** Drop the keyword hostile filter from the design; it is theatre. Instead: lookup routes and the menu declare `effect: read` in code, `prepare` routes require `allowedUserIds` to be non-empty and to include the author (the same gate as `answer` corrections), and the golden set gets a hostile block whose expected type is `unclear` or `status`, never `work`. Add "fail-open allowlist is a blocker for shipping `prepare` routes to Discord" as a precondition in the Action.

### 8. Memo and menu records hold raw operator text; the scorecard must not leak it into the repository — `should`, Risk (privacy)

- **Verified.** `ask_corrections.normalized_text` stores the full text (`corrections.ts:75-88`), by design "only in the workspace database, never in a repository" (9-10). The report returns counts and at most three leading words (`report.ts:10-12`). The golden set forbids real Ask text (`goldenCases.ts:5-7`). The probe files in `docs/design/relay/probes/` are synthetic. Discord logs JSON lines to stdout (`logging.ts`) and `messageCreate.ts` logs author ids on refusal, not content.
- **Change.** State in the Action that the scorecard is produced by `arcadia ask report`-style counts only, that held-out messages are synthetic or paraphrased, and that any `docs/design/relay/probes/*-results-*.json` committed from a live run must be checked for operator text (today's result files contain the synthetic prompts only).

### 9. Project names that are ordinary words already mis-resolve, and name-keyed rules will make it worse — `must`, Risk

- **Verified.** `scoreReference` (`src/intake/index.ts:1406-1440`) returns 0.96 when the normalized message *contains* a candidate name or alias of ≥ 4 characters, above the 0.55 floor; `GENERIC_REFERENCE_TOKENS` excludes only `app, project, site, website, tool` (125). The `capture_thought` fallback calls `resolveProjectReference(raw, context)` on the whole message (546). The golden fixture uses alias `Songbook`; the live portfolio includes a Project the `arcadia-studio-scout` skill calls "Scout" and the operator's memory notes a "Household" Project (names not verified against the live database, which this investigation did not open).
- **Consequence.** "scout out what's blocking the PRs" resolves to Project Scout at 0.96 and is not flagged ambiguous. Any lookup route that takes "project if named" inherits this.
- **Change.** For lookup routes, resolve a Project only from a bounded argument slot (text after `for|on|in|about`, or a whole-message match), require a word-boundary match, and offer the menu when the match is a substring hit on a name that is also a dictionary word. Add golden near-misses with the live names.

### 10. Read tools can report stale state with confidence; the plan has no freshness rule — `should`, Risk

- **Verified.** `todo.ts` reads SQLite; PR state comes from `workPullRequests.ts`/`gh`; production status from `production.ts`; `arcadia now` notes the dashboard renders "exactly this payload". None of the compact renderers in the plan say when their data was observed. R1-F7 raised the same point for Way lookup (`reviews/R1-relay-critique.md`, R1-F7).
- **Change.** Every compact answer carries one `as of <time> from <source>` line, and the PR/production answers say when the last poll ran. Acceptance: a test that renders from a snapshot older than N minutes shows the age.

### 12. The scorecard needs a precision floor and a safety-zero clause, measured against the next rung — `must`, Finalization / Best practice

- **Verified.** The probe's own result: rules ahead of the 27B lowered accuracy from 75/80 to 71/80 because rules were wrong more often than the model on what they claimed (`routing-3.md`, "Rules"). The decision interface already states "rules must beat the next rung's accuracy on what they claim, and abstain on the rest".
- **Best practice, with sources.** Confidence-thresholded fallback with an explicit "None"/fallback bucket is standard: Dialogflow ES returns the top intent only above the ML classification threshold and otherwise matches the fallback intent ([Dialogflow intent matching](https://docs.cloud.google.com/dialogflow/docs/intents-matching)); Azure CLU replaces the top intent with `None` below a per-project threshold and notes that the threshold is *not applied during test-set evaluation*, so eval numbers and live behaviour differ ([CLU None intent](https://learn.microsoft.com/en-us/azure/ai-services/language-service/conversational-language-understanding/concepts/none-intent)); Rasa's fallback uses both a top-score threshold and an `ambiguity_threshold` on the gap between the top two intents, then confirms the intent with the user before an ultimate fallback ([Rasa TwoStageFallback](https://rasa.com/docs/rasa/reference/rasa/core/policies/two_stage_fallback)). Error budgets: Google's example policy treats a single class of failure consuming more than 20% of the budget as a planning-level item ([SRE Workbook, Appendix B](https://sre.google/workbook/error-budget-policy/)).
- **Where it doesn't fit.** Those systems tune thresholds from thousands of endpoint utterances; one operator produces tens per week. So: measure precision on the held-out set and *count* live corrections rather than estimating a live rate, and set the budget as an absolute ("no more than one wrong claimed route per week; zero lever/Decision mis-routes ever") rather than a percentage.
- **Change.** Acceptance for item 1: on a held-out set written by someone other than the rule author, after the rules are frozen, (a) precision of claimed routes ≥ 94% (the 27B's unseen-set score, the next free rung), (b) zero messages routed to a `prepare` or `answer` route that the key marks otherwise, (c) coverage reported per class. Add the ambiguity rule: when two routes match, show the menu rather than taking the first (the prototype takes the first by list order).

### 13. The menu: three options is defensible; "learn from the tap" and "when to show it" need the stronger rules — `should`, Best practice

- **Sources.** Hick's law: decision time grows roughly logarithmically with options and depends more on uncertainty between them than on count ([Hick's law explainer](https://helio.zurb.com/ux-research/laws-of-ux/hicks-law/)); nothing in the results fixes "three" for chat disambiguation, so three plus "Something else" is a convention, not a finding. Clarifying questions help most on short and ambiguous queries ([Aliannejadi et al., SIGIR 2019](https://arxiv.org/pdf/1907.06554.pdf)), which matches the probe's hardest cases (`stop`, `prod on?`). Learning from clarifications: LUIS's active learning suggests only low-scoring endpoint utterances for human review and warns against bulk-adding new utterances after launch, preferring patterns ([LUIS utterances](https://learn.microsoft.com/en-us/azure/ai-services/luis/concepts/utterances)); that is the same shape as the existing `patternHints` → reviewed PR path.
- **Where it doesn't fit.** Active learning assumes a labeller separate from the user. Here the operator is the labeller, so each tap is a labelled example and the cost is attention (`CONSTITUTION.md`, "Operator attention is a budget"). A menu on every low-confidence message is a tax; the dashboard already shows a Clarify First question as a `/todo` item (`ask.ts:1131-1167`, `standard-harness.md`, "Everything Arcadia needs from the operator is raised through a source `arcadia todo` reads").
- **Change.** Show the menu only when at least one route scored above an abstain floor (otherwise fall through to today's Clarify First question, which already creates the `/todo` item), cap it at one menu per Ask, and record `menu_shown`, `menu_option`, `menu_ignored` on the Ask row so "how often a menu appears" and "how often it is ignored" are the scorecard's two menu metrics.

### 14. Reuse list the plan does not mention — `could`, Missed opportunity

- Discord Decision cards with lettered options and consequences, answered by "just the letter" or `NNNN A` (`requiresReviewFormatter.ts:126-143`, `messageCreate.ts:29-37`): the menu's Discord form should be this formatter with numbers, bound to a menu id.
- Dashboard `/todo` deep links from Discord (`apps/discord-bot/src/todoLinks.ts:1-6`): the "what needs me" compact answer should end with `todoListUrl`.
- `Heard:` receipt and `type:` reply corrections (`heard.ts:25`, `askCorrection.ts:8-9`): a lookup answer should keep the `Heard: status (high, rule)` line so the existing correction path keeps working.
- `arcadia ask report` and `tests/ask-coverage.test.ts` (`src/commands/askReport.ts`, `askCoverage.ts`): the scorecard's coverage and corrected-rate are already computed there; add menu counters rather than a new report.
- `arcadia way-lookup` (`src/commands/wayLookup.ts`): the "how Arcadia works" route exists as evidence tooling with a byte budget; R1-F4/F7 caveats (no abstention, stale passages) apply and the route should say "a match is only a statement about wording", as the command already does (58-62).
- `ask show` trail (`askTrail.ts:36-46`, dashboard `/api/ask/show`): "what happened to my earlier request" is answered by id today; the new part is finding the id from a subject, which is where the menu belongs ("Did you mean: the newsletter Ask from Tuesday / the speed Ask from last week / Something else").

### 15. Finalization: what the plan must state before it becomes Actions — `must`

- The route list as `IntakeAction` kinds with their heard type (`status`), their backing command, and the compact renderer's size limit.
- The held-out set's author and freeze protocol (the probe's method, written down as the test), and the precision/safety thresholds in finding 12.
- The menu identity, binding and expiry rules (finding 6) and the exact record written on a tap (finding 5): row, columns, source value, and that it is not replayed.
- Project-name resolution for arguments (finding 9) with the live names as golden near-misses.
- The Discord allowlist precondition for `prepare` routes (finding 7).
- The freshness line on every compact answer (finding 10).
- Per-surface acceptance: a golden case passes the pure replay *and* `runAskCommand` (existing), and a renderer test asserts the dashboard `message` and Discord receipt contain the compact text.
- What I'd cut from the first slice: the learning loop (memo replay from taps), the `reason` and `capture` routes (they already exist as `Clarify First` and `work`), the hostile keyword filter, `prepare_start`/`prepare_off` on Discord until the allowlist is closed, and any new report. What I'd add: the renderer for the two routes that exist today, as the first PR.
