# Decision 0065: Decide where the long-lived Claude Code token (from claude setup-token) that managed Sessions receive as CLAUDE_CODE_OAUTH_TOKEN is stored and how the worker reads it.

## Options

- **Dedicated keychain item read at launch**: The operator stores the token as its own macOS keychain item; the worker reads it with security find-generic-password at each launch and passes it only into the Session environment. Nothing is written to disk in plain text, but it depends on the worker launchd context being able to read the keychain, which is the same access that failed in #568, so it must be proven first.
- **Owner-only file in the workspace config** (recommended): The operator writes the token to a 0600 file under the workspace config directory, outside every repository; the worker reads it at launch and passes it only into the Session environment. Works from any launchd context and is simple to rotate, but the token sits in plain text on disk, protected only by file permissions and disk encryption.
- **Worker launchd environment**: The token goes into the worker LaunchAgent EnvironmentVariables, so every process the worker spawns inherits it. Least code, but the plist is regenerated by the restart-services script (so it must be preserved there) and every child process, not just coding-agent Sessions, can read the token.

## Rationale

Issue #568: a worker-launched claude-code-cli Session could not use the interactive keychain sign-in and waited on /login. A long-lived token removes that interruption, but storing and passing a credential crosses the Constitution credential boundary, so the operator decides the storage. The operator generates the token; no agent handles its value.
