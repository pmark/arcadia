# Decision 0123: Decide the spend bound for the first managed production run on Arcadia own repository, which today has no provider-window awareness and no operator reserve.

## Options

- **Codex only, gate on, attended first run** (recommended): Name only codex-cli in the production policy and remove capacityGateEnabled false from the workspace config (operator-owned). Launches are admitted only while the windows Codex reports (today only a 7d window, 4 percent used) are fresh (15 minutes, a live read) and under 95 percent used; at 95 percent new launches stop on their own (the margin is checked only at admission: a running Session and its resumes can push the window to 100 percent, and only the 120 minute limit or a provider-limit stall stops it), a standing refusal is logged once per episode and, after 5 consecutive ticks (10 minutes), raises a red alert shown first in production status with the capacity reason and a notification, while a shorter wait appears only in the worker log and timeline. The 5 percent last-slice margin is the only protection for your own Codex use on the shared account, and the 20 percent reserve of Decision 0111 is not built. Claude Code and OpenCode are not used. Concurrency stays 1, Sessions stop at 120 minutes, an Action gets 3 attempts, and with no integration grant the worker spends only on development Sessions while a supervising agent reviews and merges each PR. Enabling the gate also applies to managed-launch enrollment (a managed launch refuses capacity_unavailable when the selected provider is not admitted); operator launches are not capacity-checked. Draft PRs exist only with remote preservation (otherwise preservation is local only and the merge is the local merge command); with remote preservation and no integration grant the worker pushes branches and opens draft PRs but runs no reviewer and never readies or merges. Without a packet_approval delegation each of the 7 packets needs your arcadia review approve with no-execute; adding the delegation needs an expiry and brings #1012. The first run is attended: you or a supervising agent merge each PR before the next launches. I would also add the missing production preview flag for the Session time limit so 120 minutes can be lowered, and show a standing capacity wait reason in production status before the 10-minute alert, as small follow-up Actions.
- **Gate off, structural bounds only, attended first run**: Leave capacityGateEnabled false and rely on the allowlists, concurrency 1, the 120 minute Session limit, 3 attempts per Action, the failed-Run budget and merge-by-supervisor pacing. Both Claude Code and Codex stay usable and nothing is refused for a stale observation. There is no awareness of provider windows: unattended Sessions can drive the shared allowance window (Claude 5h and 7d, Codex 7d) to 100 percent and use up your interactive allowance until it resets, and the only protection is that a provider already at 100 percent is rejected from selection. Cheapest to start, weakest bound.
- **Wait for the reserve and burn rate**: No unattended run on Arcadia own repository until Decisions 0103 and 0111 are built: the governed-roles Plan Actions build-operator-presence-proof, select-model-for-delegated-task, broker-delegation-requests, reserve-operator-emergency-capacity and project-token-burn-rate are all open in a Plan that is currently a draft, and would have to be reactivated and finished first. Gives a real 20 percent operator reserve and a projected-burn throttle. The slowest option, and the bug Plan waits.
- **Codex and Claude Code, gate on, after a small build**: First build a small Action that refreshes the Claude Code usage snapshot unattended (nothing in the worker does today; this makes the worker read your Claude Code OAuth credential from the keychain or the credentials file and call the Anthropic usage endpoint, which is credential use and needs its own explicit Decision), then enable the gate with both providers. Both windows become real bounds and either provider is refused when stale or at 95 percent, but the capacity gate still does not substitute another provider once a launch is bound (the launch preview may select and record an alternate provider before a packet exists when hard provider evidence requires it, Decision 0063, but it never changes a bound provider), no reserve, and a refusal is visible only as the 10-minute red alert. Adds a build step before the first run; Codex is selected first anyway on cost rank, so it buys little for the bug Plan.

## Rationale

Operator request 2026-10-11 (prep the spend bound; readiness gate 2). Verified read-only against origin/main 7c3f0cd29. Unattended Sessions draw on the same Claude Code and Codex accounts you use interactively. With capacityGateEnabled false every provider reads unmetered by config. Enabling the gate today admits Codex (live app-server read, 7d window 4% used), refuses Claude Code as capacity_stale (its usage snapshot is 71 hours old and nothing unattended refreshes it) and refuses OpenCode as manual_receipt_expired (no probe), with no capacity-gate substitution once a launch is bound (the launch preview may select and record an alternate provider before a packet exists when hard provider evidence, such as a provider at 100 percent or a launch-precluding adapter gap, requires it, Decision 0063, but it never changes a bound provider) and a refusal that reaches production status only as a red alert after 5 consecutive ticks (10 minutes). Decisions 0103 and 0111 (percent-of-window budget, 20 percent reserve) are approved but unbuilt: their Actions are open in a draft Plan, so only the fixed 5 percent last-slice margin exists. Real bounds today: provider and Project/Plan/Action allowlists, concurrency 1, 120 minute Session limit (not settable on tick launches), 3 development attempts per Action, failed-Run budget 8 per Milestone, light-tier session start, and merge-by-supervisor pacing (no integration grant). A short Grant expiry does not bound spend. Cost per Action is unmeasured; one typical Action is one light-tier Session, with no integration grant the code-capped worst case is 3 development attempts per Action plus uncapped resumes (reviewer calls, up to 5 QA and 5 code-review per input, run only under an integration grant).
